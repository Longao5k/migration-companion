## 2. ADR-012：联邦来源 403 的处置

**状态：Accepted / 部分为外部依赖**

### 背景

三个联邦 connector（`home-affairs-news`、`home-affairs-190`、`home-affairs-491`）每轮全部返回 `FetchRejected: source returned HTTP 403`。这三个恰好是冻结白名单里价值最高的页面：联邦公告、190、491。它们不可用，等于产品的"官方政策证据"只剩南澳一半。

### 403 的成因判断

按可能性排序：

**H1（最可能）：站点边缘的 bot 管理拒绝了"不像主流浏览器"的客户端。**
支持证据：403 从两个完全不同的网络复现；`www.` 与 `immi.` 两个主机同样被拒；同时搜索引擎仍能索引这些页面（说明存在对已验证爬虫的放行）。我们的客户端触发的信号包括：Python `urllib` 的 HTTP 行为与 TLS 指纹、缺 `Accept-Language`、`Accept-Encoding: identity`（浏览器一定会声明 gzip/br）、无 `Sec-Fetch-*` / `Sec-CH-UA`、仅 HTTP/1.1、无 cookie、无历史 TLS 会话。

**H2（次要，且被部分证伪）：IP / ASN 信誉。** 云主机 ASN（腾讯云新加坡）常被 bot 管理降权，叠加非澳洲地理位置。但 403 从另一个完全不同的网络同样复现，因此这**至多是叠加因素，不是根因**——换服务器位置不能可靠解决问题。

**H3（叠加因素）：突发请求形态。** 一轮里三个联邦 target 连续发起、无间隔、无抖动。请求总量很小，单独不足以致 403，但会加重 H1 的判定。

**H4（可排除大部分）：路径/主机专项规则。** 例如针对遗留的 `/news-subsite/Pages/*.aspx`。但 `www.homeaffairs.gov.au/news-media` 同样 403，说明不是单一路径问题。

**H5（必须花很小成本排除）：robots.txt 实际上就是拒绝的，而我对代码的推断有误。** 见下方诊断步骤第 1 条。

### 决策

#### D1. 立即把三个联邦来源 `enabled` 置为 `false`（本轮必做）

站点已用 403 明确拒绝我们的自动化访问。继续每 6 小时、每天 12 次（3 个 URL × 4 轮）敲同一个拒绝我们的站点，**本身就是不受欢迎的自动流量**，并且直接违反基线第 15.3 节：「收到来源方停止请求、条款变化或技术封锁时暂停 connector 并进入人工评审；不技术绕过」。

配套：在 `Source` 上记录停用原因与日期（`lastFailureCode` 已存在，建议新增 `pausedReason` / `pausedAt`），后台采集健康页显示为「已暂停：站点技术拒绝」。

#### D2. 修复「没有监控」被显示成「没有变化」（产品正确性缺陷，本轮必修）

现在联邦来源全挂，`GET /v1/content/changes` 返回空，App 的 `ChangeLogScreen` 显示「暂时没有可公开的变更证据」。在联邦监控完全失效的情况下，这句话读起来像**「联邦政策没有变化」**——这对一个以"政策变更证据"为卖点的产品是不可接受的误导，也踩到冻结规则 2.1「故障不发布」的精神：故障不能被静默呈现为"无事发生"。

要求：公开接口新增来源覆盖状态（已监控 / 已暂停 / 从未成功），App 在资讯与变更两个页面显式呈现「联邦来源当前未纳入自动监控，请以官方页面为准」。这条与 403 是否修好无关，必须先做。

#### D3. 诊断动作（全部合法，均不涉及规避）

1. **把 robots.txt 的取用改为显式请求**：用与页面请求相同的 `CRAWLER_USER_AGENT` 取 robots.txt，记录 HTTP 状态码与内容 hash，再交给解析器。这同时解决三件事：排除 H5、消除"robots 用一个身份、页面用另一个身份"的不一致、以及满足基线「robots 不可达时停止而不是假设允许」需要能**区分**三种结果。
2. **保存 403 的响应头与有界响应体**（建议前 2 KB）进证据存储。边缘拒绝页通常含一个 reference / ray id，联系站方时必须提供。当前代码在 `HTTPError` 分支直接丢弃 body。
3. **遵守 `Crawl-delay`**：`legislation.gov.au` 明确声明 `Crawl-delay: 10`，我们当前完全不读。按主机串行 + 遵守声明值 + 抖动 + 指数退避。
4. 记录 403 是否稳定（三个 URL 是否同时、是否随时间变化）。

#### D4. 允许与禁止的调整——一条可执行的判断标准

> **如果一项改动的目的是让对方的自动化防护把我们识别成"别的客户端"，它就是禁止的；如果目的是让对方更容易识别我们、并降低对方负载，它就是允许的。**

**允许**（更可识别、更低负载）：

- 保留并强化真实可联系的 `User-Agent`（含 bot 说明页 URL）；
- 增加 `From:` 头（RFC 9110 定义的运营者邮箱）；
- 增加 `Accept-Language: en-AU`（真实表达我们要的语言）；
- 启用 gzip（减少对方带宽，这是减负，不是伪装）；
- 按主机串行、遵守 `Crawl-delay`、抖动、指数退避、每日请求上限；
- 提高 `CRAWLER_INTERVAL_SECONDS`，为不同来源设置不同间隔。

**禁止**（本轮明令，任何人不得"顺手修一下"）：

- 把 `User-Agent` 改成 Chrome / Safari / Googlebot 或任何非我们自己的标识；
- TLS / JA3 / JA4 指纹伪装、`curl-impersonate`、带 stealth 插件的无头浏览器；
- 更换出口 IP、住宅/移动代理、第三方 unblocker 或 scraping API、把爬虫挪到住宅网络；
- 验证码识别或人工打码；
- 重试轰炸、并发试探；
- 用第三方抓取结果、Google 缓存或 archive.org 副本**替代**被拒的源（既是同一意图的规避，且存档副本对"当前政策"这个产品定位本身就不成立）；
- 以上任何一项"仅在开发机上试一下"。

#### D5. 合法替代路径（按优先级）

| # | 路径 | 现状 | 说明 |
| --- | --- | --- | --- |
| A1 | **联系 Home Affairs 请求放行我们的具名爬虫** | **未做，需要产品所有者** | 用站点的联系/反馈渠道，附 D3.2 拿到的 reference id、爬虫说明页 URL、请求频率承诺。记录申请日期、渠道、答复。**在拿到书面确认前，不得记为"可用"。** |
| A2 | **官方订阅/通知渠道** | **未验证** | Home Affairs 的 news/media 页面提及订阅服务；我们的自动化检查被 403 挡住，需要人工用普通浏览器确认是否有邮件订阅或 RSS。若有：订阅到运营邮箱 → 编辑手工建条目。**这不是抓取**，完全落在冻结规则允许的人工录入内。绝不做"收邮件→自动解析→自动发布"。 |
| A3 | **legislation.gov.au 官方 Public API** | **已查证存在**，条款未确认 | `https://api.prod.legislation.gov.au/swagger/v1/swagger.json` 返回 "Legislation Public API" v1（OData 风格，全 GET，未声明鉴权）。用它监控 Migration Act 1958、Migration Regulations 1994，**以及真正承载职业清单与收入门槛的移民立法文书**。按版本元数据（编制号、登记日期）判变化，信噪比远高于抓页面文本。前置条件：向 OPC 确认使用条款与速率限制；把 `api.prod.legislation.gov.au` 作为**独立来源条目**加入白名单；对 `www.legislation.gov.au` 遵守 `Crawl-delay: 10`。 |
| A4 | **data.gov.au（CKAN API）** | 数据集存在 | Home Affairs 在 data.gov.au 发布签证项目统计（开放许可）。适合做**派生统计内容**，**不适合政策变更检测**。不要拿它冒充政策来源。 |
| A5 | **确认页面级版权/许可立场** | 未确认 | 联邦材料**可能**适用 CC BY 一类开放许可。但许可管的是**再利用**，不是**访问**——即使是 CC BY，也不授权绕过技术封锁。结论写进 `Source.licenseNote`，由澳洲合资格人士签核。 |
| A6 | **退回人工录入** | **已具备能力** | `POST /v1/content/admin/news`（`CreateNewsDto`）与更正流程已可用。审核员用普通浏览器打开官方页面，记录 URL + 日期 + 有限引用 + 原创中文摘要。变更监控则改为对少量高价值联邦页面的**定期人工核对**（建议每周）。这是诚实、可辩护、当天就能执行的方案，代价是审核员工时。 |

**A6 是当前唯一不依赖外部答复就能恢复联邦内容的路径**，应立即启用，不要等 A1/A2。

### 原因

- 冻结规则把"不绕过网站技术限制"写成了产品规则，不是建议。403 是站点的技术限制，规避它同时违反冻结规则、可能违反站点条款，并把公司暴露在与政府部门的直接冲突里——这对一个以"官方证据可信"为卖点的产品是自毁性的。
- 换服务器位置这类"看起来无害"的做法，在 H1 成立时既解决不了问题，又会把一次工程尝试变成一次规避尝试的证据链。
- legislation.gov.au 的官方 API 是本轮查证到的**唯一确定可用的新增机器可读联邦来源**，且它覆盖的正是"职业清单/门槛"这类真正影响申请人的内容。

### 后果

- 联邦覆盖在 A1/A2 有结果前依赖人工，审核员工时增加。这是必须接受的成本，不是可以用技术手段"省掉"的。
- 爬虫需要一次结构性改造（显式 robots 请求、Crawl-delay、退避、403 证据留存、每来源间隔）。这次改造对 ADR-017 的扩展也是前置条件，不重复投入。
- 三个联邦来源停用后，`sourceHealth` 后台与 App 都必须显示暂停原因，否则会产生 D2 描述的误导。

### 遗留项

- A1 的联系与答复：外部依赖，工程不签核。
- A2 是否存在官方订阅/RSS：需人工用普通浏览器确认。
- A3 的使用条款、速率限制、稳定性承诺：需向 OPC 确认；在确认前只做低频试用，不写进上线依赖。
- 生产节点上 robots.txt 的真实 HTTP 状态：需按 D3.1 改造后取证。

## 3. ADR-013：App 内打开官方页面

**状态：Accepted with constraints**

### 背景

产品所有者要求资讯详情能在 App 内打开官方页面看全文，并保留来源链接。当前 `home_screen.dart::_StorySheet` 与 `change_log/change_log_screen.dart::ChangeDetailScreen` 都用 `launchUrl(..., mode: LaunchMode.externalApplication)`，会跳出 App。

### 决策

#### D1. 默认方案：系统内置浏览器视图，不是裸 WebView

用已有依赖 `url_launcher: ^6.3.2` 的 `LaunchMode.inAppBrowserView`，在 iOS 上映射到 **SFSafariViewController**、Android 上映射到 **Chrome Custom Tabs**。**不新增依赖。**

理由：

- 它运行在**独立进程**里。App 侧没有任何注入 JS 或读取页面 DOM 的能力，也就**不存在"页面内容影响 App"的通道**——这一整类风险（包括基线威胁模型里的"网页 prompt injection"）被结构性消灭，而不是靠逐项配置去关闭。
- 它**显示真实 URL 与锁标**。用户能自己确认这是 `immi.homeaffairs.gov.au` 而不是我们。这同时服务于冻结规则「不得暗示官方隶属」。
- 它使用系统浏览器的证书校验、安全浏览与更新机制。Android WebView 在部分老设备上更新滞后。
- 零新增依赖、零 SBOM 变更、零隐私 manifest 变更。

#### D2. 只有产品明确需要 App 自有工具栏时，才升级为 `webview_flutter`

若必须有收藏 / 分享 / 语言切换的自有工具条，才引入 Flutter 官方的 `webview_flutter`（iOS `WKWebView`、Android `WebView`）。届时以下配置**缺一不可**，且必须写成可测试的断言：

| 要求 | 具体做法 | 防的是什么 |
| --- | --- | --- |
| **不注册任何 JavaScript channel** | 不调用 `addJavaScriptChannel`（Android 侧不调用 `addJavascriptInterface`） | 这是页面 JS 进入 Dart 的**唯一**通道，一个都不能有 |
| **非持久化数据存储** | iOS `WKWebsiteDataStore.nonPersistent()`；Android 关闭时 `WebStorage.deleteAllData()` + `CookieManager.removeAllCookies()` | 官方站点的 cookie/localStorage 不与 App 共存、不跨会话保留 |
| **Android 关闭本地访问** | `setAllowFileAccess(false)`、`setAllowContentAccess(false)`、`setAllowFileAccessFromFileURLs(false)`、`setAllowUniversalAccessFromFileURLs(false)` | 这些正是 WebView 能读到 App 私有目录（加密 SQLite 文件、加密备份包）的路径 |
| **导航白名单** | 只允许已批准的官方主机在 App 内加载；其他主机（含官方页面上的第三方外链、社交分享、`mailto:` / `tel:`）交给系统处理 | 防止官方页面上的外链把用户带到一个"看起来还在我们 App 里"的第三方页面 |
| **绝不注入凭据** | 不附 `Authorization`、不带我们的 cookie、不带账号或设备标识；**我们的 API 域名不允许在这个 WebView 里加载** | WebView 与我们的 API 不共用任何凭据 |
| **不注入 JS 改写页面** | 不做阅读模式、不删页头页脚、不改样式、不加翻译覆盖层 | 见 ADR-014 与 D4 |
| **关闭下载与文件选择** | 官方页面上的 PDF 下载交给系统浏览器；WebView 不接管文件选择器 | 避免打开用户相册/文件，与最小权限冲突 |
| **仅 https、混合内容禁止、证书错误不忽略** | `MIXED_CONTENT_NEVER_ALLOW` | 基础传输安全 |

#### D3. iOS / Android 合规要点

- **Apple**：App Review Guideline 2.5.6 要求浏览网页的 App 使用 WebKit 框架与 WebKit JavaScript——即只能是 `SFSafariViewController` 或 `WKWebView`，不能自带引擎。使用 `SFSafariViewController` 时，Apple 要求**不得遮挡、不得修改其界面、不得在其上叠加内容**；因此"自有工具条"与 SFSafariViewController 是互斥的，这正是 D2 存在的原因。Guideline 4.2（最低功能）针对"只是把网站包起来"的 App——本产品有大量原生能力，不属于该情形，但资讯模块不能演化成"整个 App 就是官方网站外壳"。
- **Apple / Google 隐私申报**：如果我们记录用户打开了哪条官方链接，这属于"浏览历史 / 产品交互"数据，必须在 App Privacy、`PrivacyInfo.xcprivacy` 与 Google Play Data safety 中如实申报。**技术默认：不记录 URL 级行为**，最多记录聚合计数。这与基线第 16 节的日志字段 allowlist 一致。
- **Android**：设备可能没有支持 Custom Tabs 的浏览器，必须回落到 `LaunchMode.externalApplication`（现有代码已在用该模式，改造时保留为回落分支）。系统返回键在内置视图内应先返回上一页再退出（Custom Tabs 自带该行为）。
- **可访问性**：内置浏览器视图沿用系统字号与对比度设置，优于我们自绘的正文渲染。

#### D4. 与「不把官方全文作为自有内容重新发布」的关系

这是本节最重要的一段，工程实现必须按它判断。

**用户设备直连官方站点：** 请求由用户设备发出，内容从官方服务器直达用户的浏览上下文。**我们的服务器不制作、不存储、不分发任何副本。** 用户看到的是官方站点的原始版式、日期、免责声明与更正；官方一改，用户下次打开就是改后的。这与用户自己在 Safari 里打开该页面没有实质区别。这也正是"URL 必须可见、必须保留官方外观、不得注入或改写"的原因——一旦我们改写，这个"等同于用户自己浏览"的性质就破坏了。

**我们转发全文：** 我们的服务器取得官方正文、存进我们的数据库、再经我们的 API 发给 App 渲染。这构成**复制 + 向公众传播**，需要许可；同时我们成为发布者，要为时效性、完整性与上下文缺失负责，并且抹掉了官方页面上的日期与例外说明。冻结规则 6.5 与基线 15.3 明确禁止。

> **判定线：内容从哪台服务器出去，副本存在哪里。**
> 只要 App 里出现的官方正文是**我们的 API 返回的**，无论 UI 长得多像浏览器，都属于重新发布。
> 只要是用户设备直接向官方主机发起的请求，就不是。

由此推出的不可越界规则：

- **不缓存官方页面 HTML 到 App 本地供离线阅读。** 那是我们制作的副本，且离线内容会过期到与官方不符。WebView 只使用系统浏览器的常规缓存，我们不额外持久化。
- **不做服务端渲染代理**、不做"去广告阅读模式"、不做整页翻译覆盖层。整页机器翻译是对官方文本制作**演绎作品**，比原样展示风险更高，且翻译错误会被读者当成官方口径。
- 允许的组合只有一种：**我们自己的中文摘要 + 有限的原文片段引用（配额见 ADR-014）+ 打开官方页面。**
- 若采用 D2 的自有工具条，工具条**不得遮挡官方内容主体**，并且必须明确标注"这是外部官方网站"。

### 后果

- `_StorySheet` 与 `ChangeDetailScreen` 的按钮从 `externalApplication` 改为 `inAppBrowserView`，并保留"用外部浏览器打开"的次级入口（部分用户依赖自己的翻译扩展或密码管理器）。
- 官方页面可能不适配移动端、有 cookie 横幅、加载慢——**这些我们不修，也不应该修**。需要明确的超时与失败文案，以及"改用外部浏览器"的出口。
- 中国大陆网络下 `immi.homeaffairs.gov.au` 可能很慢或不可达。这是用户网络问题，不计入我们的可用性目标，但 UI 必须有超时提示，不能无限转圈。

### 遗留项

- `LaunchMode.inAppBrowserView` 在项目固定的 Flutter 3.47.1 + `url_launcher: ^6.3.2` 组合下的**双平台真机行为，本评审未验证**。改造时必须补真机证据。
- 若最终引入 `webview_flutter`，需走依赖评审（SBOM、隐私 manifest、双平台真机回归），并计入 Flutter 3.47.1 兼容矩阵。
- 是否需要自有工具条，是产品决定；本 ADR 只给出两条路径各自的硬约束。

## 4. ADR-014：政策变更对比的展示与存储边界

**状态：Accepted**

### 背景

产品所有者要求「全文对比」（改前/改后完整对照）。现有 evidence 存储确实保存了规范化全文（`storage.py` 的 `SourceState.normalized_text`），技术上做得到。问题不是能不能做，是做到多大范围仍然是"引用以说明变化"，多大范围就变成了"提供官方原文的替代品"。

**一个必须先说清楚的实测事实：** `migration.sa.gov.au/news` 的规范化正文只有 **2,219 字符**，而 `IngestChangeDto` 允许 `oldExcerpt` 与 `newExcerpt` **各 2,000 字符**。也就是说，按现在的规则，**一条变更记录就能把这类页面的全文公开出去**——而且是通过**无需登录**的公开接口 `GET /v1/content/changes`。这不是理论风险，是当前代码的实际能力。

### 决策

#### D1. 公开侧拒绝整页对照；后台审核侧接受完整对照

- **拒绝**把"改前/改后完整对照"作为面向用户的公开功能。
- **接受**在内容运营后台（已鉴权、有审计）提供完整对照。审核员本来就必须逐字比对官方页面，这是他们的工作前提，且是内部使用、不向公众传播。
- 后台的完整对照**读证据存储，不经公开 API**；页面必须带管理员鉴权 + 审计事件 + `X-Robots-Tag: noindex` + `Cache-Control: no-store`。
- 证据存储保持既有定位：**内部证据与差异重现，不是内容分发源**。

#### D2. 公开侧的可执行配额

| 维度 | 硬上限 | 理由 |
| --- | --- | --- |
| 单个变化片段的官方原文 | **300 字符** | 足够看清一句话或一个条件改了什么 |
| 每侧上下文 | **120 字符** | 定位用，不构成可替代阅读 |
| 单条记录公开的片段数 | **5** | 超出显示「另有 N 处变化，请打开官方页面」 |
| 单条记录官方原文合计 | **1,200 字符** | |
| 占该页规范化正文的比例 | **≤ 20%**，与上一行**取更小者** | 防止短页面被整页搬运——见背景里的 2,219 字符实测 |
| 同一来源 24 小时内公开合计 | **3,000 字符** | 防止把一次变化拆成多条绕过单条上限 |

比例上限是这张表里最关键的一行。没有它，字符数上限对短页面完全失效。

#### D3. 三处强制，不依赖单点

1. **生成端** `services/crawler/migration_crawler/diffing.py`：现在把所有 diff 行拼成两个大字符串再截断到 2000。改为结构化片段列表 `[{op, oldText, newText, contextBefore, contextAfter, blockIndex, locator}]`，每片段独立计数，超额部分**只留计数不留正文**。
2. **写入端** `services/api/src/content/content.dto.ts`：`IngestChangeDto` 的 `@Length(0, 2000)` 收窄到 `1200`，并在 `ContentService.ingest()` 增加合计与比例校验（需要 worker 同时上报 `normalizedLength`）。
3. **读出端** `ContentService.changes()` 的公开投影再截一次。**这一层不能省**：库里已有的行是在旧规则下写入的，不能假设历史数据合规，而 `changes()` 是唯一的公开出口。

#### D4. 结构化片段的附带收益

把"整页一条、所有 diff 行拼在一起"改成片段列表，同时解决三个问题：

- 审核员可以**逐片段**判断重要度，而不是对着一大坨 diff 猜；
- 一个页面能产出**多条可独立审核、可独立发布**的记录 → 同样的抓取产出更多可发布条目（见 ADR-017）；
- 每个片段带 `blockIndex` / `locator`，可以稳定地跳回官方页面的对应位置。

数据库最小改动：`ChangeLog` 保留 `oldExcerpt` / `newExcerpt`（向后兼容），新增 `fragments Json?`、`truncatedCount Int @default(0)`、`normalizedLength Int?`。

#### D5. 法律定位（工程护栏，不是法律意见）

- 300 / 1,200 / 20% 不是法律条文，是一条**可执行、可测试、可被审计**的工程线，用来把"引用以说明变化"和"提供原文替代品"分开。它的价值在于它是确定的、能写进测试的。
- 澳洲版权法下的 fair dealing（报道新闻、评论等）是**逐案判断**且要求充分标注，**不能当成一揽子许可**。
- 联邦与南澳材料**可能**适用 CC BY 一类开放许可。若适用，允许范围会大得多——但这必须由澳洲合资格人士**逐来源、逐页面**确认后写进 `Source.licenseNote`。在此之前一律按最保守配额执行。**本评审不认定任何来源已获许可。**
- 即使确认为 CC BY，仍要求署名、注明是否修改、不得暗示官方背书；整页机器翻译仍属演绎，需单独判断。

### 原因

- 冻结规则 6.5 与基线 15.3 已经写死「只保留内部证据、必要短差异、原创中文摘要和链接」。"全文对比"如果面向公开，直接与这条冲突。
- 但审核员的需求是真实的：没有完整对照，人工核实无法进行。把它放在后台既满足需求又不产生对外传播。
- 配额必须是数字，不能是"尽量少"。"尽量少"在实现里等于没有约束——当前 2,000 字符就是这么来的。

### 后果

- 变更详情页的展示形态改变：不再是「修改前 / 修改后」两个大块（现在 `_DiffBlock` 就是这么渲染的），而是若干条「变化片段 + 上下文」加一个「另有 N 处变化」提示和「打开官方页面核对」。
- 需要一条回归测试：公开接口返回的任意一条 change，官方原文合计不超过配额，且不超过 `normalizedLength` 的 20%。
- **生产上目前 0 条真实变更记录。** 也就是说变更管线在生产上从未产出过一条真实 diff，任何关于 diff 质量的判断都是未验证的。建议：在投入对比 UI 之前，先积累若干条真实变更并完成人工核实，用真实样本验证片段切分与重要度分类是否可用。

### 遗留项

- 后台完整对照页的实现与审计事件定义。
- 现有 5 份快照均为 baseline，尚无第二版本可比对；片段切分逻辑需要真实的"第二次抓取"才能验证。
- `Source.licenseNote` 的逐页面法律结论：外部依赖。

## 5. ADR-015：双语内容数据模型

**状态：Accepted**

### 背景

产品所有者要求第一版本支持"英文原文 + 中文"。现有 schema 里 `NewsItem` 已有 `sourceTitle`（官方英文标题）、`titleZh`、`summaryZh`、`sourceUrl`。

需要先把需求拆开，因为"英文原文"有两种完全不同的含义：

- **含义 A：看到官方英文正文。** 这个需求的正确解法是 ADR-013 的打开官方页面，**不是**我们存一份英文正文再发出去。后者就是 ADR-014 判定线里的"重新发布"。
- **含义 B：App 的界面与我们的编辑内容有英文版。** 这个是正当的产品需求，且我们自己写的英文是我们的原创作品，没有版权问题。

### 决策

#### D1. 英文侧的内容边界

| 元素 | 允许 | 说明 |
| --- | --- | --- |
| 官方英文标题 | **允许**，用现有 `sourceTitle` | 短、事实性、是署名的一部分 |
| **我们自己写的**英文摘要 | **允许**，新增 `summaryEn` | 我们的原创作品 |
| 官方英文正文 | **禁止**存储并对外分发 | 走 ADR-013 的打开官方页面 |
| 官方文本的机器翻译 | **禁止**发布 | 演绎作品；且翻译错误会被当成官方口径 |
| 我们自己中文摘要的机器翻译 | 允许，但需编辑复核后才能发布 | 是我们自己的文本 |
| 变更片段（`oldExcerpt`/`newExcerpt`） | 本来就是英文（源语言），按 ADR-014 配额展示 | 必须标注为「官方原文片段（英文）」，**不得原地机翻**；若提供译文，必须与原文并列并标注为非官方翻译 |

#### D2. 最小 schema 改动（一次迁移，不新增表）

```prisma
model Source {
  // ...
  sourceLanguage  String  @default("en")   // 为将来非英文来源预留
}

model NewsItem {
  // ...
  titleEn             String?   // 我们自己的英文标题（可空）
  summaryEn           String?   // 我们自己的英文摘要（可空）
  draftSourceExcerpt  String?   // 抓取得到的英文原文片段，仅供编辑改写，永不进入公开接口
}

model ChangeLog {
  // ...
  titleEn          String?
  editorSummaryEn  String?
}

model NotificationPreference {
  // ...
  language  String  @default("zh-Hans")   // 通知语言，与界面语言分开存
}
```

#### D3. 顺带修掉一个结构性隐患

`ContentService.ingestNews()` 现在把英文 `dto.sourceExcerpt` **直接写进 `summaryZh`**。目前有两道保护：`isPublished: false`，以及发布时 `assertChineseEditorialCopy` 会因为没有中文字符而拒绝。所以**没有对外泄漏**。

但这个结构是：一个名为 `summaryZh` 的字段里装着英文原文，靠一个字符集检查兜底。一次配置失误或一次绕过 `assertChineseEditorialCopy` 的代码改动，就会把官方英文正文摘录公开出去。**当前库里 6 条待审草稿正处于这个状态。**

改法：worker 写入 `draftSourceExcerpt`，`summaryZh` 在编辑改写前保持为空。`draftSourceExcerpt` 加入公开序列化的排除名单，并在 DTO 层限制长度（按 ADR-014 的片段配额，建议 ≤ 1,200）。

#### D4. 发布门必须对称，且要防"把官方英文粘进 summaryEn"

- `assertChineseEditorialCopy` 保留。
- 新增：若设置了 `titleEn` / `summaryEn` 且要发布英文版，检查它们与 `draftSourceExcerpt` / `sourceTitle` 的**最长公共子串 ≤ 120 字符**。否则编辑只要把官方英文粘进 `summaryEn`，我们就在重新发布官方正文——而且是打着"我们的英文摘要"的旗号。这个检查很粗糙，但它挡得住最可能发生的那种失误。

#### D5. API 与客户端

- **不**做 `?lang=en` 返回不同行。同一条记录一次返回全部语言字段，客户端自己选。理由：离线缓存保持一份、避免缓存键翻倍、避免"两种语言看到不同条目"。
- 每条记录附 `availableLanguages: ["zh-Hans"]` 或 `["zh-Hans","en"]`。
- **回落规则：** 英文字段为空时，显示中文内容 + 一句"该条尚无英文版本"+ 打开官方页面按钮。**绝不静默机翻**。
- Flutter 侧新增 `contentLanguage` 设置，用已有的 `shared_preferences` 持久化，**不新增依赖**。不要只跟随设备 locale——中文用户在英文系统上用这个 App 是常态。
- `NewsItem` / `PolicyChange` 的 Dart 模型加可空英文字段并保持 `fromJson` 向后兼容（现有 `fromJson` 已有 `?? ''` 的容错习惯，沿用）。

### 原因

- 现有 schema 已经把"官方英文标题"和"我们的中文内容"分开了，这是正确的骨架。双语只需要在同一条记录上加同构的英文字段，不需要拆表、不需要翻译表、不需要新的语言维度实体。
- 把"英文原文"解释成"我们存英文正文"，会直接撞上 ADR-014 的判定线。把它解释成"打开官方页面 + 我们的英文摘要"，既满足用户实际需求，又不产生任何新的版权敞口。

### 后果

- 英文摘要是**新增的编辑工作量**，不是技术开关。若没有英文编辑能力，`summaryEn` 会长期为空，产品上会呈现为"英文版内容很少"。这是运营成本问题，需要产品所有者知情。
- 通知模板需要双语，且要按 `NotificationPreference.language` 选择；推送文案仍必须泛化（基线第 12 节）。
- 一次数据库迁移，向后兼容（全部可空 + 有默认值），不需要停机。

### 遗留项

- 界面文案的国际化（`intl` 已在依赖里，但当前文案是硬编码中文）是独立且不小的工作量，本 ADR 不覆盖。
- 英文编辑人力：外部依赖。

## 6. ADR-016：用户提醒、收藏、评论、发帖的基础设施评估

**状态：技术评估，范围裁决属于产品经理**

> 本节只回答"技术上需要什么、代价多大、有哪些硬门槛"，**不裁决做不做、做多少**。

### 6.1 必须先分成两类

这四项不是一个量级的东西，混在一起谈会导致误判。

- **4a 提醒、收藏：私有用户数据。** 只有用户自己可见，不产生对外传播，不改变产品的法律性质。
- **4b 评论、发帖：公开 UGC。** 产品从"内容发布方"变成"UGC 托管方"，一次性触发三条新的合规轴（应用商店 UGC 政策、澳洲在线安全法规、诽谤风险）。

### 6.2 4a（提醒、收藏）：技术上可推进

| 能力 | 现状 | 缺什么 |
| --- | --- | --- |
| 收藏 | App 内 `toggleBookmark(item.id)`，**仅客户端** | 服务端 `ContentBookmark(accountId, entityType, entityId, createdAt)`，随账号级联删除 |
| 关注/提醒 | `NotificationPreference`（`policyUpdates`、`jurisdictions`、`tags`、`importantOnly`、`timezone`）+ `NotificationOutbox` 已存在并跨设备保存 | 按条目关注（`ContentFollow`）；`timezone` 字段有了但**没有摘要批次与 quiet hours 的实现**；APNs/FCM 实际投递是既有外部依赖 |
| 材料提醒 | 本机提醒已有 | 账号用户跨设备提醒依赖上面的 Outbox |

工程量小，不引入新的合规类别。但有两点必须写进设计：

1. **收藏与关注列表是用户签证意图的画像**（关注 190 还是 491、关注哪个职业标签）。属于敏感相邻数据：不得进日志、不得进分析、不得出现在推送文案里，账号删除时必须一并清除并纳入现有 7 天撤回与删除账本。
2. 这些数据目前会落在**新加坡节点**上。该节点已经存着账号邮箱与项目元数据，所以不是新的数据类别，但它**扩大了可关联的画像**。迁到澳洲 cell 之前，需要在 APP 8 跨境评估里一并覆盖。

### 6.3 4b（评论、发帖）：技术基础设施清单

以下是"能上架"的最小集合，不是"做得好"的集合。

| # | 基础设施 | 现状 | 说明 |
| --- | --- | --- | --- |
| 1 | 身份与准入 | `Account` + `emailVerifiedAt` 已有；nginx 已有按 IP 限流骨架（`infra/server/migration-companion-ratelimit.conf`） | 需要新账号冷却期 + 每账号/每 IP/每设备三层限流。不允许匿名发帖 |
| 2 | 数据隔离 | 无 | 独立 schema `community`，**不与 `workspace` / `files` 建立任何外键**。v1 不支持附件——我们没有独立病毒扫描 Worker，且云文件已关闭（门 M5） |
| 3 | 审核队列 | `ReviewStatus` 模式可借鉴 | 必须是**独立队列 + 独立角色**（内容编辑 ≠ 社区审核）；预审/后审可切换；SLA 计时器 |
| 4 | 举报 | 无 | 举报类型、去重、阈值自动隐藏、处置结论、申诉记录、不可变审计 |
| 5 | 屏蔽/静音 | 无 | 用户级双向屏蔽在**查询层**生效；管理员级封禁/禁言状态机 |
| 6 | 删除与账号注销 | 账号删除有 7 天撤回 + 最小 HMAC ledger | 帖子墓碑；账号删除时对已发内容的处置（删除 vs 匿名化）必须与既有删除账本一致，不能出现"账号没了但帖子还挂着实名" |
| 7 | 内容安全 | 无 | 纯文本存储 + 安全渲染（不接受 HTML、不自动加载外链图片——防 SSRF 与追踪像素）；外链域名白名单或纯文本展示；**PII 扫描拦截护照号/TFN/银行卡**——本产品的用户在评论里贴证件号是高概率事件，这不是理论风险 |
| 8 | 通知扇出 | `NotificationOutbox` 可复用 | 需要独立 dedupe 与按帖静音 |
| 9 | 可观测 | 无 | 举报量、审核时延、自动隐藏率、申诉改判率 |

### 6.4 三条硬门槛（技术无法绕过，必须记录）

1. **应用商店 UGC 政策。** Apple App Review Guideline 1.2 对 UGC App 要求**同时**具备四件事：内容过滤机制、举报机制、屏蔽滥用用户的能力、发布的联系方式。Google Play 有等价的 UGC 政策。**缺任何一项是直接拒审**，不是"上线后再补"。这意味着上表第 3、4、5、7 项是上架前置，不是后续迭代。
2. **澳洲在线安全法规。** Online Safety Act 2021 的投诉机制与 Basic Online Safety Expectations 要求可执行的下架流程与响应时限，以及一个真实的联系渠道。**这需要澳洲合资格人士判断适用范围，工程不签核。**
3. **移民协助边界。** 用户之间就个案互相"建议"，正是冻结规则 7.1 要防的事——而且这次是发生在**我们的平台上、由我们分发**。技术上只能做关键词/启发式标记 + 显著提示，**不能保证**。这是产品与法律裁决，不是工程能解决的。

### 6.5 运营成本

当前 8 个来源的人工审核已经是瓶颈：6 条新闻草稿待审、0 条变更记录。UGC 审核是完全不同的量级（不可预测的到达率、需要覆盖夜间与周末、需要处理申诉）。PM 评审第 9 节已经把"人工审核运营成本被低估"列为残余风险；4b 会把这个风险放大一个数量级。

### 技术侧记录（不是范围裁决）

4b 在技术上不阻塞，但在满足以下条件之前，**不得开启任何公开可见的 UGC 写入路径，包括"仅内测可见"**：独立的社区审核角色、举报/屏蔽闭环、上表第 1–7 项、以及澳洲法律签核。

理由很简单：内测用户也是真实用户，内容一旦对第三人可见，法律事实就已经产生，"这只是内测"不构成任何抗辩。

## 7. ADR-017：内容量与地域扩展

**状态：Accepted**

### 背景

产品所有者观察到"资讯数据量不够"，提出从南澳扩到全澳洲。这个因果推断需要先检验。

**当前内容量不足的实际构成：**

| 原因 | 证据 | 扩地域能解决吗 |
| --- | --- | --- |
| 3 个最高价值的联邦来源被 403 拒绝 | 每轮全部失败 | **不能**。扩到其他州不会让联邦页面可达 |
| 冻结白名单里已批准的 SA 页面只实现了一半 | PM 6.5 列了 8+ 个 SA URL，`sources.json` 只有 4 个 | **不需要扩**，这是补齐已冻结范围 |
| 6 条新闻草稿卡在人工改写 | 数据库 6 条 draft、5 条已发布（种子） | **不能**，反而会加重 |
| 变更管线在生产上从未产出真实 diff | 5 份快照全是 baseline、0 条变更记录 | **不能** |
| 每页只产出一条粗粒度变更候选 | `diffing.py` 把所有 diff 行拼成两个字符串 | **不能** |

**结论：内容量当前受限于审核吞吐与联邦可达性，不是抓取覆盖范围。**

### 7.1 扩到全澳洲在技术上意味着什么

#### 来源数量

| 类别 | 估算 |
| --- | --- |
| 8 个州/领地 × 每州 6–10 页（提名要求、职业清单、材料清单、处理时间、各 stream 页、新闻） | 50–80 |
| 联邦签证与公告页 | 10–15 |
| 相关立法文书（职业清单、收入门槛等以立法文书形式发布） | 20–40 |
| **合计** | **80–135 个 source target，是当前的 10–17 倍** |

#### 抓取频率与请求量

- 100 个 target × 4 轮/天 = **400 次页面请求/天**；若各州都做新闻发现，再加 200–400 次/天。总量 **600–800 次/天**。
- 字节：SA 新闻列表页单次 **247 KB**，且**该站不返回 ETag / Last-Modified**（实测 `state.json` 中两者均为 `null`）——条件请求在这类站点不生效，等于每轮全量下载。100 个 target × 200 KB × 4 轮 ≈ **80 MB/天**。字节量本身不是问题。
- **真正的问题是礼貌性。** 必须做到：按主机串行、遵守 `Crawl-delay`（`legislation.gov.au` 声明 10 秒）、抖动、指数退避、每日请求上限。**当前代码这五项都没有。** 在 8 个来源时这只是不规范；在 100 个来源时，这会让我们看起来像一次分布式抓取，重演联邦 403。

#### 架构必须改的三件事（不改就不能扩）

1. **注册表统一。** `sources.json` 打进镜像 → 加一个来源要改代码 + 重新部署；同时数据库 `Source` 行由 worker 上报**反向创建**，形成两个注册表、两份真相。必须改为**数据库是唯一注册表**，worker 通过已鉴权接口拉取"已批准且启用"的来源，`sources.json` 只作为初始种子。100 个来源靠改代码来运营是不可行的。
2. **调度器。** `service.py` 是单进程顺序循环：一个慢来源拖住整轮；没有每来源独立间隔、没有并发上限、没有按主机的礼貌间隔、没有失败退避。必须改为按来源调度（`intervalSeconds`、`nextRunAt`、失败指数退避、每主机串行 + Crawl-delay）。
3. **证据存储。** `LocalEvidenceStore` 写容器本地磁盘，README 自己写明是开发适配器。80–135 个来源的证据必须进私有对象存储 + 生命周期 + KMS，且证据保留期与用户材料分开（基线第 16 节）。轻量实例的本地盘既小又无备份。

另外，`Source.jurisdiction` 现在是自由文本 `String @length(1,32)`。8 个辖区时拼写差异会直接导致筛选与通知匹配失效（`NotificationPreference.jurisdictions` 是数组匹配）。扩展前必须收敛为受控取值。

#### 人工审核 SLA——这是真正的瓶颈

粗估：每个页面每月变化 1–4 次 → 100 个来源 = **100–400 个候选/月** = **每工作日 5–20 条**。每条 MAJOR/IMPORTANT 需要审核员打开官方页面比对、判断影响、写中文摘要，按 10–20 分钟计 = **每天 1–6 小时合格双语审核工时**，再加新闻草稿改写与英文摘要（ADR-015）。

即 **0.5–1 名全职双语内容审核**，且必须覆盖周末（政策公告常在周五发布）。

没有这个人，扩源只会把"未发布积压"做大——因为冻结规则要求重大/重要必须人工核实才能发布，用户看到的内容量**不会增加**。

#### 存储

证据字节量不是问题（100 来源 × 每周 1 个新版本 × 200 KB ≈ 1 GB/年）。问题是**位置与保留策略**，见上面第 3 条。

#### 法律

每个新州站点都要单独做 robots / 条款 / 版权审核（冻结规则 6.5 与基线 15.3）。8 个州 = 8 份独立审核。**这是外部依赖，工程不签核**，也是扩展的真实前置条件。

### 7.2 不扩范围提升内容量的技术手段（按性价比排序）

| # | 手段 | 性质 | 预期效果 |
| --- | --- | --- | --- |
| 1 | **修好联邦 403**（ADR-012） | 恢复既有范围 | 直接恢复 3 个最高价值来源 |
| 2 | **补齐冻结白名单里已批准但未实现的 SA 页面** | **不是扩范围，是补齐已冻结范围** | PM 6.5 列了 `migration.sa.gov.au/`、`/before-applying/visa-options-and-pathways/skilled-migrants`、`/before-applying/work-in-sa/occupation-lists/occupations-list`、`/how-to-apply` 以及 190/491 各 stream 页；`sources.json` 只实现了 4 个 SA 页。**可立即增加 6–10 个来源，零范围扩张** |
| 3 | **清掉审核积压** | 运营 | 6 条草稿已经抓到手，卡在人工改写。当前内容量受限于审核吞吐 |
| 4 | **SA 新闻历史回填** | 既有来源纵深 | `NEWS_DISCOVERY_LIMIT` 现为 6（上限 12）且只抓第一页。一次性回填历史新闻，立刻获得纵深 |
| 5 | **按 heading/block 切分差异**（ADR-014 D4） | 同样抓取，更多产出 | 一个页面产出多条可独立审核、可独立发布的记录，而不是"整页一条" |
| 6 | **按来源设置抓取间隔** | 时效性 | 处理时间、职业清单这类高变化页面 1–2 小时；静态页面 24 小时。注意 SA 站不返回 ETag，判重靠内容 hash（现有代码已经这么做） |
| 7 | **接入 legislation.gov.au 官方 API**（ADR-012 A3） | 新增机器可读联邦来源 | 覆盖真正影响申请人的职业清单与门槛，按版本元数据判变化，信噪比高 |
| 8 | **自有原创内容 + 从我们自己的快照派生的结构化内容** | **零版权风险，真正的差异化** | 中文时间线、术语解释、"这次变化影响哪一类申请人"的中性说明；处理时间趋势图、职业清单增删对照表——这些是**我们自己的数据集**，官方站点没有。（事实本身不受版权保护，但汇编/数据库权利需法律确认） |

### 决策

1. **不以扩地域解决内容量问题。** 第一阶段维持 SA 190/491 + 必要联邦上游的冻结范围。
2. 立即执行 7.2 的第 1–5 项，它们全部落在已冻结范围内。
3. 第 7 项（legislation.gov.au API）作为新增来源，需走来源审批流程（robots / 条款 / 许可结论写进 `Source.licenseNote`），不是"顺手加一条"。
4. 扩到全澳洲的前置条件写死为四条，**缺一不可**：注册表统一到数据库、按来源调度器 + 礼貌性控制、证据进私有对象存储、以及**已到位的 0.5–1 名全职双语审核**。前三条是工程可以自己完成的；第四条不是。
5. 8 份州级 robots/条款/版权审核是外部依赖，不由工程签核。

### 原因

- 扩地域会同时放大三个已知瓶颈（审核吞吐、礼貌性控制缺失、证据存储位置），却不解决任何一个当前的实际约束。
- 7.2 里前五项的总工程量小于扩澳所需的架构改造，且不需要任何外部签核。
- 第 8 项是唯一能让内容量增长**不受官方页面变化频率限制**的手段，同时是版权敞口最小的一项。

### 后果

- 短期内容量增长依赖运营（改写、回填），不是抓取。需要产品所有者接受这一点。
- 爬虫的调度器与礼貌性改造无论如何都要做（ADR-012 已经需要），扩澳时不重复投入。
- 若产品所有者坚持提前扩澳，技术侧的立场是：可以做，但必须先完成上面四条前置，并且明确记录"未发布积压会增长"这个后果，不能事后归因为工程问题。

### 遗留项

- 双语审核人力：外部依赖。
- 州级来源的 robots/条款/版权审核：外部依赖。
- `legislation.gov.au` API 的使用条款与速率限制：待向 OPC 确认。

## 8. 本轮明确禁止清单

在基线第 20 节的基础上追加。以下每一条都不得以"先试试""只在开发机上""内测阶段无所谓"为由执行。

**关于抓取：**

- 把 `User-Agent` 改成 Chrome / Safari / Googlebot 或任何非我们自己的标识。
- TLS / JA3 / JA4 指纹伪装、`curl-impersonate`、带 stealth 插件的无头浏览器。
- 更换出口 IP、住宅/移动代理、第三方 unblocker 或 scraping API、把爬虫挪到住宅网络。
- 验证码识别或人工打码。
- 重试轰炸、并发试探。
- 用第三方抓取结果、Google 缓存或 archive.org 副本**替代**被拒的源。
- 在站点已用 403 拒绝我们之后，继续保持该 connector `enabled`。

**关于内容展示：**

- 把官方页面正文存进我们的数据库再经我们的 API 发给 App 渲染（无论 UI 长得多像浏览器）。
- 面向公开的整页"改前/改后"对照。
- 缓存官方页面 HTML 到 App 本地供离线阅读。
- 服务端渲染代理、"去广告阅读模式"、整页翻译覆盖层、注入 JS 改写官方页面。
- 发布官方文本的机器翻译。
- 把官方英文正文粘进 `summaryEn` 当作"我们的英文摘要"。
- 在没有监控的情况下，让空列表读起来像"没有政策变化"。

**关于 WebView：**

- 在加载官方页面的 WebView 里注册 JavaScript channel / `addJavascriptInterface`。
- 给该 WebView 注入 `Authorization`、cookie、账号或设备标识。
- 在该 WebView 里加载我们自己的 API 域名。
- Android 侧开启 `allowFileAccess` / `allowContentAccess` / `allowFileAccessFromFileURLs` / `allowUniversalAccessFromFileURLs`。
- 遮挡或改造 `SFSafariViewController` 的界面。

**关于 UGC：**

- 在缺少举报、屏蔽、审核队列、联系方式任一项的情况下开启公开可见的 UGC 写入路径（含"仅内测可见"）。

## 10. 技术总监签署意见

**五项需求全部有可执行的技术路径，但其中两项必须改写产品所有者的原始表述才能实施。**

1. **联邦 403 是本轮唯一的严重问题，且它的正确解法不是技术解法。** 站点已经明确拒绝我们的自动化访问；冻结规则要求我们暂停并转人工评审，不绕过。本轮必须做的两件事是：停用三个 connector，以及**修掉"没有监控"被显示成"没有变化"这个误导**——后者比 403 本身更危险，因为它会让用户以为联邦政策没变。恢复联邦覆盖的路径按顺序是：人工录入（今天就能做）→ legislation.gov.au 官方 API（已查证存在，条款待确认）→ 请求放行 / 官方订阅（需要外部答复）。

2. **App 内 WebView 通过，但默认用系统内置浏览器视图而不是裸 WebView。** 判定线是「内容从哪台服务器出去，副本存在哪里」：用户设备直连官方站点不是重新发布，我们的 API 返回官方正文就是。这条线决定了不能做离线缓存、不能做阅读模式、不能做整页机翻——这些"体验优化"恰恰是把浏览变成重新发布的动作。

3. **"全文对比"公开侧拒绝，后台审核侧接受。** 当前 `oldExcerpt` / `newExcerpt` 各允许 2,000 字符，而实测 SA 新闻页的规范化正文只有 2,219 字符——**现在的规则已经允许通过一个无需登录的公开接口把这类页面整页发出去**。这不是未来风险，是需要本轮收窄的现状。

4. **双语通过，最小改动。** 但"英文原文"必须理解为"打开官方页面"，不是"我们存一份英文正文"。顺带修掉 `ingestNews` 把英文原文写进 `summaryZh` 的结构性隐患——目前只靠一个字符集检查兜底。

5. **UGC 的技术清单已给出，范围由产品经理裁决。** 技术侧只记录一条：在举报、屏蔽、审核队列、联系方式四件事齐备并通过澳洲法律签核之前，不得开启任何公开可见的 UGC 写入路径，**"仅内测可见"不构成例外**。

6. **不以扩地域解决内容量问题。** 内容量当前受限于审核吞吐与联邦可达性。在冻结范围内有 8 项可执行的增量手段，其中第 2 项（补齐白名单里已批准但未实现的 SA 页面）连范围都不用动就能增加 6–10 个来源。扩澳的四条前置条件里，前三条工程可以自己完成，第四条（0.5–1 名全职双语审核）不能。

以上裁决不改变基线第 23 节的五条上线硬门槛，也不改变冻结 P0 的任何一条。任何一条与冻结规则冲突的实现，都必须回到产品经理与技术总监重新评审，不得在实现阶段自行放宽。
