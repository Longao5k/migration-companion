## 2. 第 1 项：资讯详情用 App 内 WebView 打开官方页面

### 2.1 结论

**有条件采纳，纳入第一阶段，但必须按“受限内置浏览器”而不是“内容页”实现。**

### 2.2 依据

冻结规则并不禁止内嵌浏览官方页面，反而要求“每条新闻或 Change Log 都必须能回到官方来源”（2.1）、“摘要不能替代原文”（2.1）。真正的红线是三条：

1. 第 6.5 节：“不把官方或媒体全文作为自有内容重新发布。”
2. 技术总监评审第 15.3 节：“不在 App 内重建政府网站。”
3. 第 3 节：“不声称与澳洲联邦政府、南澳政府、Home Affairs 或注册移民代理机构存在官方隶属、认可或合作。”

内置 WebView 实时加载官方页面**不构成再发布**（内容仍由官方服务器提供），但若界面看起来像 App 自有内容，就会踩到第 3 条——这才是本项的主要风险，而不是版权。

### 2.3 冻结的产品规则

1. **主机白名单。** WebView 只允许加载**已批准来源主机**。官方页面内的外链、重定向到白名单外主机、`http:` 降级、`javascript:` / `data:` scheme 一律不在内置 WebView 中打开：切换到系统浏览器或显示“即将离开官方来源”提示。
2. **来源归属常驻可见。** 顶部固定显示完整域名与一行说明：这是该机构的官方网站页面，不是本产品的内容。
3. **保留原有出口。** 产品所有者要求保留来源链接——同时**不得**因为有了 WebView 就移除“在系统浏览器中打开”和“复制链接”。
4. **不注入、不留存。** 不注入脚本读取或改写页面；不把 WebView 内的正文抓取、缓存或离线保存为自有内容（否则等价于全文再发布）。
5. **会话隔离。** WebView 使用非持久化、独立于 App 账号的存储；请求不携带 App 的 `Authorization`、账号 ID、邮箱或任何用户标识，URL 中不放任何个人数据。
6. **失败态诚实。** 离线或加载失败时显示失败并给出“复制链接 / 外部打开”，**不得**退回展示本地缓存正文冒充官方页面。
7. **隐私披露。** 隐私政策须说明：通过内置浏览器访问第三方官方网站时，该网站可能收集访问信息，本产品不控制其处理行为。

### 2.4 验收口径（怎样算做完）

- 白名单外主机 100% 不在内置 WebView 中加载；自动化用例覆盖：页面内外链、跨主机重定向、`http:` 降级、`javascript:`/`data:`/`file:` scheme、超长与畸形 URL。
- 抓包证据：WebView 发出的请求不含 `Authorization` 头、账号 ID、邮箱或任何用户标识；URL 查询串中无个人数据。
- 会话结束（或退出该页面）后 cookie / localStorage 被清除，可重复验证。
- 每个已批准来源在运营后台留有“允许内嵌显示”的条款复核结论、依据与复核人；**未记录结论的来源不允许内嵌**，只能外部打开。
- iOS 与 Android 真机各覆盖不少于 5 个来源页面：加载、返回、外部打开、复制链接、离线失败态均正确。
- 界面走查：任意资讯详情页 → 内置浏览器，全程可见域名与“官方网站页面”归属说明；商店截图不使用内嵌官方页面作为主视觉（避免第 5.4 节的官方身份暗示）。

### 2.5 需专业复核

**是。** 内嵌显示第三方官方页面的站点条款、版权与商标使用，以及是否构成暗示官方关联，须由澳洲合资格专业人士在上线前复核。此前提未完成时，仍按现状使用外部浏览器打开。

### 2.6 残余风险

| 风险 | 处理 |
| --- | --- |
| 用户把官方页面误认为本产品内容 | 常驻域名与归属说明；商店素材不使用内嵌页面 |
| 官方页面自带第三方跟踪脚本 | 会话隔离 + 隐私政策披露；不注入、不留存 |
| 官方站点改版或加机器人防护导致内嵌失败 | 失败即失败，保留外部打开；不做任何规避 |

## 3. 第 2 项：政策变更“全文对比”

### 3.1 结论

**拆分裁决。**

- **采纳：完整差异对照视图。** 一条变更的**全部差异块**都要显示，每块含改前/改后文本、所在章节定位、变化类型与编辑中文说明——不再是“一行摘要”。
- **拒绝：官方页面改前/改后全文并排。** 把未变化的正文也搬进 App 与第 6.5 节“不把官方或媒体全文作为自有内容重新发布”、技术总监评审第 11 节“对外只显示支持理解变化的最短必要片段”、第 15.3 节“不在 App 内重建政府网站”直接冲突。

### 3.2 依据

冻结文档第 2.1 节对 Change Log 的字段口径是“旧/新**片段**、上下文”，不是全文。因此产品所有者说的“不只一行摘要”是**冻结文档本来就要求的**，当前实现没做到；而“改前/改后完整对照”若指整页正文，则超出冻结范围。

同时必须指出：这不是一次 UI 改动。当前 `diffing.py` 用行级 `ndiff` 把删除行与新增行分别拼接、**各截断到 2000 字符**，没有块级定位与上下文。直接在这个数据上做“全文对比”界面，只是把两坨截断文本并排，**比现在更容易误导用户**。必须先按技术总监评审第 11 节“差异算法”落地：按 heading / paragraph / list / table row 建稳定 block，保存 add/delete/replace、上下文、locator、置信度与规则版本。

### 3.3 冻结的产品规则

1. 差异块列表**不得静默丢内容**。超过展示上限时必须显式提示“差异过大，请回到官方页面查看”，不能悄悄截断。
2. **对外展示的官方原文片段总量设服务端上限**，按来源配置，客户端不可绕过；超限时只显示定位与链接。
3. 重要/重大变更仍须人工中文说明才能发布（现状保持，不放宽）。
4. 故障页面（403、验证码、空白、模板改版、404）不得生成任何对照视图——它们按第 4.5 节先视为故障候选。
5. **例外通道：** 若某来源以明确开放许可发布（例如 Creative Commons 类许可），可在**逐来源核实并记录许可条款、且经法律复核后**，对该来源放宽原文对照长度。这条属于**需要重新进行产品与法律评审的变更**，不得由工程或运营自行开启。

### 3.4 验收口径

- 一条变更的所有差异块可完整浏览；被上限截断时有显式提示与官方链接，抽样验证不存在静默丢块。
- 每个差异块显示：所在章节/定位锚点、改前文本、改后文本、变化类型、生成该差异的规则版本。
- 服务端强制片段上限：构造超限用例，API 返回被裁剪且带提示的结果；直接调用 API 也无法取得超限片段。
- 每个来源在后台记录“对外可展示原文片段上限”及其条款依据与复核人；无记录的来源使用最保守默认值。
- 爬虫 golden snapshot 回归新增对照视图用例：模板改版、导航变化、空白响应、403、PDF 换版均不得产出对照视图。
- 抽样 10 条已发布变更：对照视图中不出现资格判断、路径推荐或“你应该……”的表述（第 7.1 节）。

### 3.5 需专业复核

**是。** 对外展示官方原文片段的比例与许可依据须经复核。“全文并排”在取得逐来源书面许可或确认开放许可之前，不得实现、不得上线。

### 3.6 残余风险

| 风险 | 处理 |
| --- | --- |
| 用户把差异块当成完整政策，据此做决定 | 每屏保留官方链接与“以官方原文为准”；不做影响判断 |
| 块级差异算法误报导致对照视图无意义 | golden snapshot 回归 + 人工审核门；一般变化仍抽样复核 |
| 片段上限被逐来源放宽后失控 | 上限在服务端、按来源配置、变更需记录复核人 |

## 4. 第 3 项：第一版本至少支持英文原文和中文

### 4.1 结论

**有条件采纳，但要分清三件不同的事：**

| 含义 | 裁决 |
| --- | --- |
| (a) 详情页同时显示**官方英文原标题 + 英文原文引用片段 + 中文原创摘要** | **采纳**，纳入第一阶段 |
| (b) App 内显示官方页面**英文全文** | **拒绝**，理由同第 2 项 |
| (c) App **界面**全量英文本地化（en-AU） | **建议放第二阶段**；若产品所有者坚持进第一版，须按 4.4 的完整口径验收，不接受半成品 |

### 4.2 依据：与“不把官方全文作为自有内容重新发布”的关系

这条冻结规则约束的是**再发布**，不是**引用**。判断标准是三点，全部满足才算引用：

1. **数量最小**：只保留支持理解该条新闻/变更所必需的最短片段（第 6.5 节、技术总监评审第 11 节）。
2. **归属清晰**：界面上必须能区分“这是官方英文原文”与“这是本产品的中文概述”，且始终可跳回官方页面。
3. **不替代原文**：产品不因为提供了英文片段就宣称用户不必看官方页面。

按此标准，(a) 是引用，**不冲突**；(b) 是再发布，**冲突**。

值得指出：所需字段**已经存在**。`NewsItem.sourceTitle` 就是官方英文原标题，`ChangeLog.oldExcerpt` / `newExcerpt` 本身就是官方页面的英文原文片段。第 3 项在内容层面主要是**呈现缺口**，不是数据缺口。

### 4.3 冻结的产品规则

1. **中文摘要不得被表述为“翻译”。** “翻译”隐含准确性承诺；本产品提供的是中性中文概述。界面用词统一为“中文概述”，并注明“以官方英文原文为准”。
2. **英文原文与中文概述冲突时，以官方英文原文为准**，该说明必须在详情页可见，不能只写在条款里。
3. 第 7.1 节边界不因提供英文原文而放宽：英文片段旁边同样不得出现资格判断、成功率、路径推荐。
4. 保留 `assertChineseEditorialCopy`（发布前必须有中文原创标题与摘要）。提供英文原文**不是**跳过中文编辑门的理由。
5. 若做 (c) 英文界面：**不接受中英混排的半成品**。移民产品上，一句没翻的中文错误提示可能让用户做出错误判断。

### 4.4 验收口径

**(a) 内容双语（第一阶段）**

- 每条已发布新闻详情同时具备：官方英文原标题、官方来源链接、中文原创标题、中文概述；四者在界面上归属可区分。
- 每条已发布变更详情同时具备：英文原文差异片段（改前/改后）、中文编辑说明、来源链接、核实状态。
- 服务端新增校验：`sourceTitle` 必填且非空；与来源页面标题不一致时后台标为待核（不阻塞发布，但必须可见）。
- 抽样 20 条：中文文案中不出现“翻译”“官方中文版”“中文原文”等措辞；不出现个案资格判断。
- 英文片段长度受第 3 项的服务端上限约束，抽样验证不超限。

**(c) 英文界面（若纳入）**

- 语言切换后 100% 用户可见文案无中文残留，覆盖：导航、空态、错误态、权限提示、分享与协作文案、订阅与试用文案、通知文案、账号删除流程。
- 隐私政策、使用条款、订阅说明、免责声明、移民协助边界文案均有经复核的英文版本；未复核前该语言下不提供这些入口即视为**不通过**。
- 两种语言下分别跑一遍第 5.3 节的内容与法律抽样（不出现资格判断/路径推荐/答案建议）。
- 系统语言为英文的新安装用户默认进入英文；可手动切换并持久化。

### 4.5 需专业复核

**是。** 英文法律文本（隐私政策、条款、订阅与退款说明、免责声明）与英文界面下的移民协助边界表述，须由澳洲合资格专业人士复核；英文原文引用比例同第 2 项一并复核。

## 5. 第 4 项：提醒、收藏、评论、发帖（本轮重点）

### 5.1 先查清：冻结文档里的“评论”到底指什么

产品所有者的记忆是对的——冻结文档里**确实有“评论”**，但它指的是**项目内协作评论**，是私有的。原文如下：

冻结文档第 6.3 节「App 协作权限」：

> - **仅查看：** 查看清单和已授权文件；不能上传、**评论**、修改、外部分享或删除。下载/导出由所有者在项目级单独控制，默认关闭。
> - **可协作：** 新增文件、更新清单状态、编辑备注、**评论**和编辑自己的新版本；不能邀请成员、创建外部分享、改变权限、删除项目或删除他人文件。

冻结文档第 2.6 节「Word 编辑」中也出现“评论”，但那是 **DOCX 文档内批注**，与社交无关：

> P0 编辑格式为**受支持的简单 DOCX**：打开阅读、文字编辑、基础段落、字体/字号、粗斜体、列表、简单表格、查找替换、复制粘贴、**评论**、保存副本和受支持文档导出 PDF。

技术总监评审同样把评论放在**项目工作区**内：第 13.1 节 `workspace` schema 为“项目、申请人、清单、提醒、**评论**、成员和状态历史”；第 19 节 Slice 4 为“App 协作：邀请/接受、viewer/collaborator、delete toggle、**评论**、操作记录、冲突提示”。

**而公开社区在冻结文档第 3 节「第一阶段明确不做」中被逐字排除：**

> - **不做公开社区、公开用户资料、公开材料分享或材料市场。**

### 5.2 两件事必须分开：已实现的私有功能 vs 面向所有用户的 UGC

| | 项目内协作评论（已实现） | 公开评论 / 发帖（新需求） |
| --- | --- | --- |
| 可见范围 | 仅该项目的成员（所有者/可协作/仅查看） | 全体用户，含未登录访客 |
| 准入 | 所有者定向邀请，接收方登录并明确接受 | 任何注册用户 |
| 服务端授权 | 读走 `assertReadable`、写走 `assertWritable`；非成员无任何路径 | 需要全新的公开读写模型 |
| 内容治理 | 靠小范围熟人关系 + 界面提示约束 | 需要事前/事后审核、举报、屏蔽、申诉、封禁 |
| 冻结依据 | 第 2.4、4.3、6.3 节 **在范围内** | 第 3 节 **明确不做** |
| 当前状态 | 门 M2 已通过：成员列表、角色调整、讨论读取与发表均已闭环，界面带“不要填写证件号码、访问码或政府表格答案”提示 | 不存在，也不应存在于第一阶段 |

**结论：产品所有者记得的“评论”已经做完了，只是它在“项目 → 云端与协作管理 → 协作”页签里，是给被邀请的人看的。** 如果需求实质是“我记得有评论但我在 App 里没看到”，那是**信息架构问题**，处理方式是把项目讨论从次级页签提到项目主界面，而不是新增公开社区。

### 5.3 公开评论/发帖与冻结范围的冲突点（逐条）

**冲突一：与第 3 节“不做公开社区、公开用户资料”直接冲突。**
公开评论区就是公开社区；发帖还需要公开用户身份（昵称/头像/发帖历史），触及“公开用户资料”；用户在帖子里贴材料截图会触及“公开材料分享”。三条冻结禁令一次全中。

**冲突二：与第 7.1 节移民协助边界冲突——这是最严重的一条。**
公开发帖在移民产品上的真实内容形态就是个案建议：“我 190 打 70 分能不能获邀”“你这种情况应该走 491”“这份雇主信这样写就能过”。冻结文档第 7.1 节引用的边界是：

> 澳洲 Home Affairs 说明，使用移民程序知识协助准备申请/相关文件或就申请提供建议，属于 immigration assistance，通常只能由注册移民代理、澳洲法律从业者或法定豁免人士提供；[Migration Act 1958 第 276、280、281 条](https://www.legislation.gov.au/C1958A00062/latest/text)也覆盖准备/协助准备申请、提供建议及收费限制。

由此产生四层风险：

1. **用户之间互相提供 immigration assistance**，其中大部分人不是注册代理或法律从业者。
2. **产品运营并商业化这个渠道**（订阅制产品内的社区），是否因此被认定为促成或参与提供移民协助——**必须由澳洲移民法律专业人士判断，产品团队无权自行断言无风险。**
3. **未注册人员借平台招揽有偿服务**（“加我私聊帮你办”）是移民论坛的高频真实形态，会把产品变成非法代理的获客渠道。
4. 冻结文档第 7.1 节已经预先堵死了最常见的辩解：

> 在澳洲专业法律审查完成前，不上线任何个性化 AI、材料合规评分、缺件判断或自动申请功能。**免责声明不能挽救本身已经在提供个案协助的功能。**

**冲突三：与已收窄的数据边界冲突。**
公开发帖必然带图片上传（EOI 截图、邀请函、雇主信、护照页）。而当前：

- 产品所有者已决定 `CLOUD_FILES_ENABLED=false`，**材料文件只在用户设备上**（门 M5）；
- 服务器在**新加坡**，门 M4 已把“新加坡节点与澳洲数据驻留冲突”记为上线阻塞项，明确要求“放入任何真实申请材料前必须先完成跨境评估、合同保护与用户披露”；
- 部署中**没有独立病毒扫描 Worker**（门 M4 记录），所以上传文件会永远停在 `PENDING`。

也就是说，公开发帖要求**重新打开一条产品所有者本人刚刚关闭的“用户内容进服务器”通道**，并且要先解掉两个已知阻塞项。

**冲突四：与内容治理模型冲突。**
现有内容管线的全部设计是“有限数量的官方来源 → 抓取 → 人工审核 → 发布”，审核对象**可枚举、非对抗**。UGC 是无上限、实时、对抗性输入，治理模型完全不同。冻结文档第 9 节残余风险已经给出过判断标准：

> 人工审核运营成本被低估 → 首发只监控小规模高价值官方来源；**没有审核资源就暂停扩源，不降低核实标准。**

UGC 的审核量级远高于扩源。按同一条标准，在没有审核团队之前不能开这个功能。

**冲突五：与“无账号可用”的产品设计冲突。**
冻结文档第 2.3 节允许“浏览、创建本机项目、查看文件、基础编辑和直接文件分享无登录墙”。公开发帖必须实名到账号并建立公开身份，而当前**连正式账号体系都还没有**——内测身份是逐邮箱绑定的访问码（门 M4），产品经理在该门已明确“不接受把它写成账号体系已完成”。在正式账号体系上线前谈公开身份是空中楼阁。

### 5.4 真要做，需要承担什么

#### A. 内容审核机制

- **审核模式决策**：事前审核（发布前人工过）还是事后审核 + 举报驱动。移民个案建议的危害是延迟显现的（用户按错误建议递交后才发现），产品经理倾向**事前审核**，成本极高。
- **审核标准文档**：明确判定什么算个案移民建议、什么算代理招揽、什么算敏感材料泄露、什么算诈骗话术（“包过”“内部渠道”“加急名额”）。没有这份文档，审核员之间不可能一致。
- **审核工具**：队列、留痕、申诉、批量处理、复核抽样。注意：关键词/图片自动预筛若把用户图片送第三方服务，直接触碰第 7.2 节“不把文件内容发送给通用 AI/OCR/转换服务，除非该处理器已获批准……”。
- **SLA 与排班**：至少覆盖澳洲工作时间；诈骗、代理招揽、身份材料泄露类内容需要更短 SLA。
- **成本模型**：审核人力成本必须先算清并由产品所有者接受，而不是上线后再补人。

#### B. 举报与屏蔽

- 每条 UGC 有举报入口，举报分类明确，有处理时限与结果反馈。
- 用户可屏蔽其他用户；被屏蔽者内容对屏蔽方在**所有位置**不可见（列表、详情、搜索、通知、提及）。
- 违规内容可下架、违规账号可封禁，且有申诉通道。
- 公布可达的联系方式。

#### C. Apple App Review 对 UGC 应用的具体要求

Apple 的 [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) 第 1.2 节 User-Generated Content 要求含 UGC 的 App 必须同时具备四项：

1. **过滤机制**——阻止不当内容被发布到 App；
2. **举报机制**——用户可举报冒犯性内容，并且运营方**及时响应**；
3. **屏蔽能力**——用户可屏蔽滥用者；
4. **公开联系方式**——用户能便捷联系到运营方。

此外还需一并处理：

- **年龄分级**必须如实反映 App 内含 UGC；缺少上述控制的 UGC App 可能被要求提高分级或被拒。
- **账号体系**：公开发帖实质要求注册账号，因而 Guideline 5.1.1 的**App 内账号删除**要求适用（本产品已具备该能力），且账号删除与 UGC 的处理关系必须说明。
- **提审材料**：需要 UGC 审核流程说明、演示账号与可复现的审核演示。
- Google Play 的 User Generated Content 政策要求相当：内容审核策略、App 内举报与处置系统、屏蔽能力，并在政策与商店披露中如实说明。

以上是按当前公开政策的产品理解。冻结文档第 7.4 节已写明“商店政策会变化。每次提审和每次新增 SDK、权限、订阅产品或数据用途时重新核对官方规则”，因此**最终以提审当日的官方政策与审核结论为准**。

#### D. 法律风险（移民产品特有）

以下每一条都需要澳洲合资格专业人士出具意见，产品经理**不作结论**，只列出必须被回答的问题：

| 风险领域 | 必须被回答的问题 |
| --- | --- |
| 移民协助边界（Migration Act 1958 s.276/280/281） | 平台运营一个用户互相提供签证建议的公开渠道，是否使运营主体涉入 immigration assistance？需要哪些主动措施才落在边界内？ |
| 未注册代理招揽 | 平台对在其上招揽有偿移民服务的行为负有何种义务？需要何种主动监测与处置？ |
| 平台对第三方发布内容的责任（含诽谤） | 澳洲法下运营方对用户发布内容承担何种责任？需要何种条款、通知与下架流程？ |
| 隐私（APP / NDB） | 用户在帖子中公开第三方个人信息（雇主、代理、案件细节）时，运营方作为处理者的义务与泄露通知义务如何界定？ |
| 澳洲消费者法 | 用户因平台上的错误建议受损时，免责声明能否排除责任？（参照第 7.3 节：不能以“概不退款”排除澳洲消费者权利，同理不能以免责声明排除全部责任。） |
| 未成年人与在线安全 | 澳洲在线安全制度下的行业义务是否适用？年龄分级与年龄验证要求为何？ |

**关于公开 UGC 的完整裁决：这属于“需要重新进行产品、技术和法律评审的变更”，不能直接纳入。**

依据是冻结文档第 10 节产品经理签核的原文：

> 任何删减冻结 P0、扩大签证范围、自动上传敏感材料、引入个性化建议或降低人工核实标准的变更，都需要重新进行产品、技术和法律评审。

公开 UGC 同时触发其中三条：它是引入个性化建议的渠道（由用户提供）、它需要重新打开敏感材料上传路径、它需要一套与现有人工核实标准完全不同的治理模型。

**产品经理的建议不是“做不了”，而是排序错误。** 理由按重要性：

1. 它把产品最大的可信度资产（只讲官方事实、不给个案建议、每条都能回到官方来源）与最大的法律风险点放进同一个界面。普通用户无法区分“官方变更”和“网友说法”，而错误的个案建议在移民场景下的代价是签证被拒或被禁止再申请。
2. 它需要的能力（7×24 审核、举报/屏蔽/申诉/封禁、年龄分级、平台责任法律意见、审核人力预算）比第一阶段任何一个已冻结模块都重，而第一阶段目前连正式账号体系、生产推送、商店订阅和文档编辑授权都还是外部依赖。
3. 它要求重新打开产品所有者本人刚刚关闭的用户内容上传通道，且必须先解掉新加坡数据驻留与缺少病毒扫描 Worker 两个已知阻塞项。

### 5.6 满足真实诉求的替代方案（第一阶段可做，不产生 UGC）

产品所有者提出评论/发帖，背后的真实诉求大概率是“用户需要交流、产品需要活跃度”。以下四项在冻结范围内即可满足其中大部分：

1. **把已实现的项目讨论提到主界面。** 真实的协作对象（申请人本人、配偶、雇主 HR、用户自己的注册代理）都能被邀请进项目，讨论功能已经能覆盖。当前它藏在“云端与协作管理 → 协作”页签内，用户找不到。**零新增法律风险，纯信息架构改动。**
2. **单向反馈通道。** 用户可对某条新闻/变更提交“我看不懂”或“我认为这里有误”，直接进入运营的更正队列（第 4.5 节的更正记录机制已存在）。反馈不公开、用户之间不可见。既拿到用户声音，也不产生 UGC。
3. **官方 Q&A（编辑产出）。** 运营基于用户高频疑问产出中性中文说明，走现有人工审核门与来源标注规则，仍不做个案判断。这满足“想看别人问什么”的需求，但内容责任在运营而非用户。
4. **产品外部社群。** 若产品所有者希望有社区，可放在 App 之外的独立渠道，产品内不内嵌、不导流为核心功能。**注意：这不消除代理招揽与平台责任问题，仍需法律意见确认运营方的义务与宣传口径。**

### 5.7 若未来重新评审并批准，重新评审必须产出什么

- 完整 UGC 产品规格（内容类型、可见范围、身份模型、与项目工作区的隔离方式）。
- 审核标准文档、审核模式决策、SLA 与排班、审核人力与成本模型，并经产品所有者书面接受。
- 举报 / 屏蔽 / 申诉 / 封禁的完整流程与工具。
- 年龄分级方案与 Apple / Google 商店披露方案。
- 图片上传的重新评估：数据驻留（澳洲区域）、独立病毒扫描 Worker、隐私披露与同意。
- 正式账号体系（非内测访问码）先行完成。
- **澳洲合资格专业人士的书面法律意见**，覆盖 5.4 节 D 表中的全部问题。

**未来上线时的验收口径示例**（供重新评审参考，本轮不签核）：

- 未通过审核的内容对外 100% 不可见（含搜索、分享链接、通知、缓存）。
- 举报到处置有 P50 / P95 时限数据，且达到预先承诺的 SLA。
- 屏蔽后被屏蔽者内容在所有位置 100% 不可见，含通知与提及。
- 对抗测试：构造代理招揽、诈骗话术、贴证件图片、个案资格建议共不少于 200 条样本，**个案移民建议与代理招揽的漏放率为 0**。
- Apple / Google 提审材料含 UGC 审核说明与可复现演示；年龄分级与实际内容一致。
- 用户可导出与删除自己的 UGC；账号删除时 UGC 的处理方式经法律确认并在删除确认页明示。

## 6. 第 5 项：从南澳扩到全澳洲

### 6.1 结论

**不纳入第一阶段。** 但产品所有者的出发点（内容量不够）**成立且必须解决**——只是根因不是地域范围。本节给出六项不破坏阶段冻结即可执行的提量方案。

### 6.2 与冻结范围的冲突

- 第 8 节阶段路线：第一阶段南澳 → **第二阶段**全澳大利亚。
- 第 6.5 节：第一阶段自动监控采用官方白名单（SA + 必要联邦上游）。
- 第 3 节：不提供 SA 190/491 之外的官方清单模板。
- 第 6.6 节：“第二阶段进入全澳洲时……**不能把 SA 模板简单复制成全澳模板**。”
- 第 10 节：“扩大签证范围……需要重新进行产品、技术和法律评审。”

需要说明的是：**技术上不存在障碍。** 技术总监评审第 1.2 节已把内容模型建成 `country / jurisdiction / visa_program` 多对多，并明确“数据模型和 API 不允许出现 `sa_news`、`sa_visa_type` 等不可扩展的硬编码列”；第 19 节也写明第二阶段“只需新增 AU jurisdiction/source/template/tag 配置和容量，不重写账号、项目、分享、编辑、权限”。**真正的约束是内容运营容量与法律复核容量，不是代码。**

### 6.3 真正的瓶颈分析

#### 瓶颈 A：3 个联邦 Home Affairs 源 403 —— 覆盖面缺口，不是数量缺口

`services/crawler/sources.json` 中 8 个来源里，`home-affairs-news`、`home-affairs-190`、`home-affairs-491` 抓取返回 403，即站点的机器人防护在拒绝。**扩大地域范围不会解决这个问题——只会把同一个问题复制到另外 7 个辖区。**

**红线：不允许通过伪装 User-Agent、改用无头浏览器规避、更换出口 IP 或任何绕过反爬手段解决。** 冻结文档第 3 节“不绕过登录、验证码、付费墙、robots 或网站技术限制”与技术总监评审第 11 节“禁止绕过登录、验证码、付费墙、反机器人或 IP 限制”都是硬规则，且第 9 节残余风险表已经给出既定处理方式：白名单、页面规则、快照证据、人工复核和故障状态；不绕过访问控制。

允许的解法，按优先级（每一步都要留证据）：

1. **核实该机构是否提供官方 RSS / newsroom feed / API / sitemap**，若有则改用。技术总监评审第 11 节本来就要求“优先官方 API、RSS、sitemap 和条件请求；无必要不启浏览器”。**此项尚未核实，本文件不对是否存在这类接口作任何断言。**
2. **就机器访问向来源方书面申请并留存答复。** 爬虫 User-Agent 已被强制要求包含真实联系页（`fetcher.py` 拒绝无 `+http` 联系地址的 UA），这条路径是通的。
3. **用已获批准的替代官方来源覆盖同一事实。** 联邦立法与法定文书走 `legislation.gov.au`（该源当前可用），可覆盖相当部分联邦层面的规则变化。
4. **转为人工录入。** 第 6.5 节已明确允许：“运营可人工添加‘非官方来源’链接和原创摘要，但必须显示来源类型、原始链接和更新时间。” 官方来源同理可人工录入链接、标题与原创中文摘要并标注复核日期。**这条能立刻恢复联邦内容的可见性，完全在冻结规则内。**
5. **无论用哪条路径**，采集健康页必须把 403 显示为**失败**并告警，不能显示为“无变化”。当前 `runner.py` 已用 `report("ERROR", error_code=...)` 区分，需确认后台展示口径一致。

#### 瓶颈 B：只跑了一轮 —— 结构上不可能有 diff

`runner.py` 中 `if not previous.content_hash: return "baseline-created"`：**首轮只建基线，第二轮起才产生变更候选。** 5 个可用来源目前只有基线快照，所以“变更记录为 0”是**正确行为，不是缺陷**。

真正缺的是**周期性调度**。门 M4 的“明确遗留”已经记过这一条：“生产 evidence bucket/WORM 策略、**调度**、故障告警和人工审核 SLA。” 没有调度，就永远停在基线。

补上调度后，变更记录的增长速度取决于官方页面的**真实变更频率**——这是事实上限。扩地域可以让这个数字变大，但那是把更多辖区的真实变更加进来，不是把当前 0 变成非 0 的正确办法。

#### 瓶颈 C：6 条新闻草稿卡在人工审核门 —— 运营缺口，不是产品缺口

爬虫发现 6 条（`discover_sa_news` 默认 limit=6），全部 `isPublished=false`。服务端 `assertChineseEditorialCopy` 要求发布前必须有中文原创标题与摘要——**这正是第 2.1、4.5 节要求的门，不能为提量绕过。**

因此“内容量不够”当前**最直接**的原因是：**没有人把这 6 条草稿审完发布。** 审 6 条草稿是小时级工作；扩到全澳洲是季度级工作，且需要重新法律复核。

#### 瓶颈 D：冻结白名单里已批准但尚未接入的来源还有一批（最重要的发现）

把冻结文档第 6.5 节的白名单与 `services/crawler/sources.json` 实际接入的 8 条逐一比对，**以下来源已在冻结白名单内、已获批准，但尚未接入**：

| 已批准但未接入的来源 | 说明 |
| --- | --- |
| `https://migration.sa.gov.au/` | 首页与 Latest News（当前只接了 `/news`） |
| `https://migration.sa.gov.au/before-applying/visa-options-and-pathways/skilled-migrants` | Skilled Migration 总览 |
| `https://migration.sa.gov.au/before-applying/work-in-sa/occupation-lists/occupations-list` | **SA 职业清单——变更频率高、对用户价值最高** |
| `https://migration.sa.gov.au/how-to-apply` | 申请流程主页 |
| `https://www.legislation.gov.au/F1996B03551/latest/text` | **Migration Regulations 1994** |
| SA 190/491 各 onshore/offshore stream 页面 | 第 6.5 节要求“由运营后台维护明确 URL 清单；新增页面必须先通过差异规则与人工审核试运行” |

**结论：在完全不动阶段冻结的前提下，监控来源数量还有接近一倍的空间，且这些来源不需要任何新的法律复核——它们已经在冻结白名单内**，只需按第 6.5 节完成 robots / 站点条款 / 版权用法记录与首轮差异规则试运行。

#### 瓶颈 E：感知问题——“0 条变更”当前显示为空白

变更列表为 0 时呈现为空态，用户看到的是“这个产品没内容”。但事实是“监控中的 5 个来源本周没有经核实的政策变更”，这**本身就是有价值的信息**。这一条不增加任何内容量，却直接解决“数据量不够”的感知。

### 6.4 不破坏阶段冻结的提量方案（按投入产出排序）

| 序 | 动作 | 预期效果 | 依据 |
| --- | --- | --- | --- |
| 1 | **审核并发布已有 6 条新闻草稿**（保留人工中文摘要门） | 公开新闻从 5 条增至最多 11 条，**当天可见** | 第 2.1、4.5 节 |
| 2 | **接入第 6.5 节已批准但未接入的来源**，优先 **SA 职业清单**、How to apply、Migration Regulations 1994 | 监控页面数从 8 增至 13+ | 第 6.5 节（无需新法律复核） |
| 3 | **3 个 403 联邦源转人工录入 + 采集失败告警**，同时按 6.3-A 的路径 1/2 寻找官方 feed 或书面许可 | 恢复联邦内容可见性 | 第 6.5 节允许人工录入；第 3 节禁止绕过 |
| 4 | **上周期性调度**，所有可用来源至少每日一轮；采集健康页显示每源最近成功/失败/未变化并对连续失败告警 | 第二轮起才会有真实变更记录 | 门 M4 遗留项 |
| 5 | **在来源条款允许范围内回补 SA 官方新闻列表的历史条目**（代码上限 12，`NEWS_DISCOVERY_LIMIT` 可调），仍是“链接 + 英文原标题 + 原创中文摘要”，不是全文转载 | 单项合规增量最大 | 第 6.5 节 |
| 6 | **变更为 0 时显示监控状态而非空白页**：本周无经核实的政策变更 + 监控中来源清单 + 最近检查时间 | 直接改善“数据量不够”的感知 | 第 4.5 节（发布内容显示来源与时间） |

### 6.5 若确实需要扩范围，必须重新评审什么

冻结文档第 10 节已写明扩大范围需要重新进行产品、技术和法律评审。具体到全澳洲，重新评审必须覆盖：

1. **来源白名单**：另外 7 个州/领地各自的提名主页、职业清单、申请要求、处理时间；**每个来源逐个**做 robots / 站点条款 / 版权复核并记录结论与复核人（第 6.5 节、技术总监评审第 11 节）。
2. **模板与内容**：第 6.6 节明确“不能把 SA 模板简单复制成全澳模板”。各州提名要求不同，模板必须逐州做内容与法律复核。
3. **人工审核容量与 SLA**：第 9 节的既定标准是“没有审核资源就暂停扩源，不降低核实标准”。扩到 8 个辖区意味着监控页面数与审核队列量级上升，必须**先有排班再扩源**。
4. **通知与筛选模型迁移**：`NotificationPreference.jurisdictions` 默认为 `["AU-SA"]`。扩地域后要设计默认值与迁移策略——**老用户不能被静默订阅全澳内容**。
5. **法律复核**：各州内容的移民协助边界与免责表述须由澳洲合资格专业人士再次确认（第 7.1 节）。
6. **商店与文案**：App 描述、截图若从“南澳”改为“澳洲”，须同步核对不暗示政府官方身份（第 5.4 节）。

**产品经理建议：先按 6.4 的六项解决内容量瓶颈，用两到四周的真实运行数据（每周新增经核实变更条数、审核耗时、用户打开率与留存）再决定是否提前启动第二阶段。** 这与第 8 节“第二阶段按数据决定州/领地加入顺序”的既定原则一致——用数据决定，不用“感觉少”决定。

### 6.6 验收口径

- 采集健康页对每个来源逐条显示：最近成功时间、最近失败时间与错误类别、连续失败次数；**3 个 403 来源显示为失败而非“无变化”**，且有告警记录。
- 调度上线后连续 7 天有运行记录；至少完整跑通一次“真实 diff 候选 → 人工审核 → 发布或忽略”。
- 6 条草稿全部处置（发布或明确忽略并记录原因）；公开新闻条数与后台已发布条数一致。
- 第 6.5 节白名单内未接入的来源全部接入，或逐条记录不接入的原因；每个新接入来源有 robots / 条款 / 版权复核记录与首轮差异规则试运行结论。
- 联邦内容在 403 未解决期间以人工录入方式保持可见，并明确标注来源类型与“人工录入”。
- **代码走查确认无任何绕过反爬的实现**：逐条检查 User-Agent 取值、出口代理配置、无头浏览器启用条件；`fetcher.py` 对 robots 不可达时“停止而非假设允许”的行为保持不变。
- 变更列表为 0 时显示监控状态页而非空白页，含监控来源数与最近检查时间。
- 无任何州/领地被扩入 `sources.json` 或内容标签体系——**第一阶段仍是 SA + 必要联邦上游**。

### 6.7 残余风险

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 为提量而绕过反爬 | 违反冻结规则，来源方封禁或法律风险 | 明列红线；代码走查纳入验收；来源方要求停止时暂停 connector 并人工评审 |
| 为提量而降低人工审核标准 | 错误政策解读推给用户 | `assertChineseEditorialCopy` 与重要/重大人审门保持不变，任何放宽须重新评审 |
| 补齐后内容量仍不足以支撑留存 | 商业假设不成立 | 这本身就是有价值的第一阶段结论；用数据决定第二阶段时点，而不是提前铺开 |
| 官方页面真实变更频率低 | “变更记录少”长期存在 | 用监控状态页把“无变化”变成可信信息，而不是空白页 |
